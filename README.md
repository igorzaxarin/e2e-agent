# Рабочее место тестировщика

Архитектура системы — это пайплайн из шести субагентов. Их задача превратить сырые бизнес-требования в связанные end-to-end сценарии.

**Жизненный цикл сценария**:

1. **Траектория**. Аналитик выделяет пользовательский путь (user journey) и прослеживает его сквозь систему.
2. **Замкнутый цикл**. Путь передается в итерацию «проектирование → ревью».
3. **Параллелизм**. Пайплайн не ограничивает количество активных ветвей. Вы можете запустить столько независимых циклов, сколько требует масштаб продукта, насколько это возможно в рамках используемой модели.
4. **Критерий остановки**. Шлифовка длится до тех пор, пока шаг не избавится от структурных противоречий. Итерации повторяются до полного устранения блокеров.
5. **Human-in-the-loop**. При обнаружении пробелов генерация останавливается. Система эскалирует вопрос человеку вместо того, чтобы маскировать неопределенность допущениями. Это гарантирует полноту покрытия требований.

```
input/requirements/*.md
        │
        ▼
[requirements-analyst] ──► output/suites/J01-….md + _index.json   journey, этапы, пробелы
        │
        ▼
  ❓ шлюз требований — вы видите каждый непокрытый REQ, каждый пробел и каждый
     блокирующий вопрос и выбираете, сколько циклов запустить параллельно
     и чем владеет один цикл
        │
        ├──────────────────┬──────────────────┐   P конкурентных циклов, по journey на каждый
        ▼                  ▼                  ▼
[qa-designer J01]   [qa-designer J02]   [qa-designer J03]  ──► output/cases/J0N-…/
        ▼                  ▼                  ▼
   review_scope ──► ничего не изменилось? journey → NEEDS_HUMAN, без вызова критика
        ▼                  ▼                  ▼
[test-critic J01]   [test-critic J02]   [test-critic J03]  ──► output/reviews/, output/state/J0N.json
        │                  │                  │
        ├── blockers > 0 и iteration < 2 ──► обратно к дизайнеру этого journey
        └── blockers = 0 ──────────────────► этот journey готов, остальные продолжают
        │
        ▼
  ❓ [опционально] генерация pytest — оркестратор спрашивает, нужны ли pytest-тесты
        │
        ├── да ──► pytest-stub-writer на каждый journey с вердиктом PASS → output/tests/<J>/
        │            └── с --selenium: адресация UI, три слоя ↓
        │                 [скрипт] инвентарь → [ui-cartographer] карта → [browser-test-writer] код
        └── нет ──► переход к шлюзу покрытия
        │
        ▼
  ❓ шлюз покрытия — требования, которые не проверяет ни один кейс; открытые вопросы
        │
        ▼
   output/report.md
```

## Требования к окружению

- Gigacode CLI (субагенты + пользовательские Markdown-команды)
- Python 3.9+ для линтеров (только стандартная библиотека)
- `selenium` — только для браузерных тестов и тестирования реальных веб-страниц

## Быстрый старт

```bash
cd <project root>
gigacode                   # запустить CLI в корне проекта
/agents                    # убедиться, что шесть проектных субагентов загружены
/e2e:run                   # полный цикл по input/requirements/*.md
```

Положите свои требования в `input/requirements/` и удалите образец.

## Команды

| Команда | Что делает |
|---|---|
| `/e2e:run [path] [--max N] [--parallel N] [--unit journey\|area] [--journey J01] [--yes] [--no-ask]` | Полный прогон: анализ → циклы «дизайн/ревью» → [опционально генерация pytest] → отчёт |
| `/e2e:analyze [path]` | Только планы journey, затем отчёт о пробелах и вопрос по пробелам |
| `/e2e:design J01 [J02 …] [review-path]` | Тест-кейсы; несколько id journey запускаются параллельно |
| `/e2e:review J01 [J02 …] [N]` | Только ревью, по одному критику на journey, параллельно |
| `/e2e:status` | Текущие артефакты, вердикты по каждому journey, открытые вопросы, вывод линтера |
| `/e2e:add [path] [--name <corpus>]` | Принять требования, сохранить их в собственной `input/requirements-<name>/`, проверить, что фабрика их читает, и спросить, запускать ли прогон |
| `/e2e:profile <log dir>` | Куда завершившийся прогон потратил токены и ходы, действительно ли субагенты работали конкурентно, какие запросы упали, обрезались или вернули пустоту |

Флаги генерации тестов у `/e2e:run`: `--generate-pytest`, `--writers sequential|parallel`,
`--selenium`, `--base-url <addr>`, `--selenium-url <addr>`, `--app-source <path-or-URL>`,
`--harvest-ui`, `--publish-allure`, `--allure-project-id N`.

`--max N` по умолчанию **2**. 

## Параллельные циклы

Аналитик запускается один раз — journey можно сформировать, только обработав все требования сразу. После
этого каждый journey получает собственный цикл «дизайнер→критик», и циклы идут конкурентно.

Сколько их — решаете вы. `/e2e:run` спрашивает:

- **сколько параллельных циклов** — 1, 2, 3 или по одному на journey (`--parallel N` отвечает заранее)
- **чем владеет один цикл** — одним journey или одной функциональной областью с последовательной
  проработкой её journey (`--unit journey|area`)

Цикл эксклюзивен: он читает и пишет только план сьюты своего journey, каталог кейсов, ревью и
`output/state/<JOURNEY_ID>.json`. Агрегатный
`output/state.json` пишет один лишь оркестратор. Journey завершаются независимо: один, ушедший в
`NEEDS_HUMAN`, не задерживает остальных.

## Обработка неполных требований

Отсутствие информации в требованиях трактуется как критический отказ (fail-stop). Модель не делает допущений, а эскалирует проблему пользователю:

*   **Результат анализа:** Вы получаете исчерпывающий реестр пробелов: непокрытые `REQ-XX`, логические противоречия со ссылками на конфликтующий текст, блокирующие вопросы (отсортированные по количеству затрагиваемых этапов), этапы без привязки к требованиям (*journey*) и ошибки группировки сценариев.
*   **Варианты действий:** 
    *   Зафиксировать выявленные пробелы и продолжить генерацию.
    *   Предоставить ответы немедленно.
    *   Остановить прогон для корректировки исходных требований.
*   **Обратная связь:** Ответы пользователя сохраняются в `input/requirements/_answers.md`. При перезапуске аналитика эти данные интегрируются в контекст как формальные требования. Сгенерированные на их основе сценарии перестают считаться гипотетическими.
*   **Автономные прогоны:** Флаг `--yes` пропускает только финальное подтверждение запуска. Флаг `--no-ask` полностью отключает интерактивность: все отложенные вопросы накапливаются в `output/pending.md` и автоматически включаются в итоговый отчет (`output/report.md`) под заголовком «Требуются решения человека».

## Браузерные тесты: фабрика селекторов

Генерация UI-тестов запускается исключительно при явном указании флага `--selenium`. Главная архитектурная проблема — использование моделью неуказанных в требованиях локаторов — решается через трехслойную фабрику данных с жесткими контрактами между этапами:

| Этап | Исполнитель | Артефакт |
| :--- | :--- | :--- |
| 1. Инвентаризация | Скрипт извлечения | `output/ui/selectors.json` (полный список доступных хэндлов) |
| 2. Привязка | Агент `ui-cartographer` | `output/ui/<J>-map.json` (карта соответствия шага кейса конкретному хэндлу или заявленному пробелу) |
| 3. Кодогенерация | Агент `browser-test-writer` | Тестовые файлы, строго следующие карте из п. 2 |

**Важное разделение ответственности:** Поиск элементов в DOM — задача скриптов обхода. Выбор конкретного идентификатора из сотен похожих для абстрактного описания «поле ввода телефона» — работа модели. Наличие промежуточной карты позволяет провести статическую верификацию тестового покрытия до написания первой строки кода.

### Происхождение селекторов и Shadow DOM

Система классифицирует источники адресов по уровням доверия (тирам):
*   **Тир A (Контракт):** Селекторы, извлеченные напрямую из исходного кода приложения.
*   **Тир B (Наблюдение):** Селекторы, собранные с работающего стенда (включая открытые `shadow roots`).

Приоритет всегда у Тира A. Если элемент присутствует в обоих источниках, используется Тир A. Тир B часто является единственным рабочим вариантом для приложений с инкапсуляцией стилей (например, Shadow DOM с хэшированными именами классов), где дерево компонентов недоступно при анализе сырого репозитория.

**Правило изоляции ожиданий:** Карта привязки содержит только адресацию. Любые поля вида `expected`, `visible`, `text` или `state` внутри файла карты являются ошибкой конфигурации (`BLOCKER`), которую пресекает скрипт `check_ui_map.py`. Поведение элемента определяется требованиями, а не результатами парсинга страницы.

Если инвентарь пуст, шаги помечаются декоратором `@pytest.mark.skip` с указанием номера незакрытого вопроса. Отчет честно отражает отсутствие гарантии прохождения, вместо того чтобы выдавать ложноположительный результат.

Закрытые контексты (`mode: 'closed'`) технически недостижимы для внешнего скрипта. Система различает состояния «контейнер не найден» и «внутри контейнера нет целевых узлов».

## Шлюзы контроля (Exit Codes)

Управление потоком осуществляется через коды завершения утилит. Любой неназванный код интерпретируется как фатальная ошибка фазы. Единообразие статусов: **код 2 означает невозможность проверки**, это никогда не эквивалент успеха.

| Скрипт | Охраняемый инвариант | Коды выхода |
| :--- | :--- | :--- |
| `validate_cases.py` | Структурная целостность JSON/Markdown кейсов (до семантики) | `1`: Блокеры структуры |
| `check_state.py` | Валидность индекса аналитика и условий прерывания цикла | `1`: Невалидный файл состояния |
| `check_artifacts.py` | Соответствие выходных данных плану этапа | `1`: Несоответствие артефактов |
| `review_scope.py` | Факт внесения изменений дизайнером | `3`: Изменения отсутствуют (дизайнер ничего не менял) |
| `check_ui_map.py` | Корректность карты шаг→селектор перед кодогенерацией | `1`: Выдуманные хэндлы или протёкшие ожидания |
| `check_selectors.py` | Наличие всех используемых селекторов в инвентаре | `1`: Селектор отсутствует в `selectors.json` |
| `parse_run_args.py` | Синтаксис аргументов командной строки | `2`: Прерывание до старта Фазы 1 |
| `run_state.py` | Порядок переходов между фазами и консистентность очереди | Критическая рассинхронизация хранилища и диска |

Скрипт `run_state.py` выполняет роль распределенного замка (*distributed lock*) и журнала транзакций. Он атомарно фиксирует текущую фазу и очередь задач. Это обеспечивает детерминированное возобновление прерванного прогона: система точно знает точку останова, исключая попытки угадать состояние. Команда `show` возвращает код 1 при обнаружении расхождений между внутренним буфером и директорией `output/state/`, запрещая старт с поврежденного слепка.

### Линтер тестовых кейсов

Выполняется агентом-критиком до начала смыслового ревью для отсечения мусорных данных:
\`\`\`bash
python3 scripts/validate_cases.py output/cases
python3 scripts/validate_cases.py examples/J01-onboarding-first-play --json /tmp/lint.json
\`\`\`

Классификация дефектов:
*   **BLOCKER:** Пустые обязательные разделы, плейсхолдеры, сломанная нумерация шагов, размытые результаты («успешно», «работает»), основной путь короче 8 шагов, отсутствие взаимодействия с собственными тестовыми данными, десинхронизация Markdown/JSON.
*   **MAJOR:** Неатомарные шаги, неиспользованные фикстуры, разрыв непрерывности состояния во второй половине сценария, вариантные кейсы без ссылки на базовый, отсутствие экспортного JSON.

Код выхода `1` сигнализирует о наличии хотя бы одного блокирующего дефекта.

## Проектные решения

1. **Сценарии (Journey), а не чек-листы.** Аналитик обязан строить сквозные пути, пересекающие минимум три функциональные области и переносящие состояние (данные) между ними. Изолированные проверки одной сущности запрещены.
2. **Жесткая классификация ошибок.** В бэклог попадают только объективные блокеры (выдуманное поведение, неопределенность результата). Все остальное маркируется как рекомендации, предотвращая бесконечные циклы правок из-за стилистических разногласий.
3. **Требования как единственный источник истины.** Молчание спецификации порождает вопрос человеку, но никогда — правдоподобно звучащий ожидаемый результат.
4. **Файловое взаимодействие (Disk-as-IPC).** Передача контекста между итерациями происходит через файловую систему. Это гарантирует идемпотентность, исключает потерю данных при сбросе контекста LLM и позволяет распараллеливать циклы записи без гонки состояний.
5. **Изоляция Journey.** Один цикл обработки владеет ровно одним сквозным сценарием. Совместное владение несколькими путями запрещено во избежание кросс-загрязнения фактов и распространения выдуманного поведения.
6. **Верификация по факту, а не по заявлению.** Вместо самооценки агента («я ничего не менял») используются криптографические доказательства. Циклом управляет сравнение SHA-256 хэшей деревьев артефактов.
7. **Детерминизм вывода.** Весь пайплайн работает при \`temperature: 0\`. Жесткий детерминизм обеспечивает поведенческую стабильность батчинга.
8. **Человек в контуре принятия решений.** На точках ветвления (недостающие требования) модель останавливается. Данные пользователем ответы становятся частью контракта.
9. **Доменно-независимые шаблоны.** Пример домена «Звук» находится только в примерах. Перенос системы на новый продукт не требует изменения ядра агентов.

## Процедура адаптации под другой продукт

1. Подмените содержимое каталога \`input/requirements/\`.
2. При несоответствии формата целевой команды скорректируйте \`docs/format.md\`, шаблон \`templates/test-case.md\` и схему валидации в начале \`scripts/validate_cases.py\`. Агенты читают контракт из файлов.
3. Для браузерных тестов укажите источник фронтенда через \`--app-source\` (репозиторий) или соберите карту UI с живого стенда через \`--harvest-ui\`. Инвентарь селекторов генерируется заново на каждом прогоне и игнорируется Git.
4. Конфигурация агентов в \`.gigacode/agents/\` остается неизменной.
