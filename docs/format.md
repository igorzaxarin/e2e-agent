# Эталонный формат e2e тест-кейса

**JSON — первичный формат, Markdown порождается из него** скриптом `scripts/json_to_md.py`.
Дизайнер пишет только `.json`; `.md` никто не правит руками — правка в нём теряется при
следующей генерации.

Направление выбрано по замеру, а не по вкусу. Обратное преобразование `.md → .json` не полно:
таблица шагов не несёт колонки с якорем REQ, поэтому `steps[].requirements` из Markdown
восстановить нечем. Прямое — полно: на реальном кейсе `json_to_md.py` воспроизвёл рукописный
Markdown строка в строку. Цена — JSON на 17 % длиннее Markdown на тех же восьми кейсах, то есть
столько же лишних выходных токенов; она платится за то, что расхождение форматов становится
невозможным по построению, а не по аккуратности.

Всё, что ниже описано в терминах Markdown, — контракт **порождаемого** файла: по нему работают
линтер, человек на шлюзе и читатель отчёта. Схема JSON — в § 5 и в
`.gigacode/skills/json-case-schema.md`.

## 1. Обязательные поля

| Поле | Что должно быть указано |
|---|---|
| **ID** | Уникальный идентификатор тест-кейса |
| **Название** | Краткое описание проверяемого сквозного сценария |
| **Цель** | Что именно подтверждает тест |
| **Приоритет** | Критический, высокий, средний или низкий |
| **Предусловия** | Состояние аккаунта, системы и данных до начала проверки |
| **Тестовые данные** | Пользователь, номер телефона, треки, исполнители, плейлисты и другие данные |
| **Шаги** | Последовательные действия пользователя |
| **Ожидаемый результат** | Конкретный результат для каждого шага |
| **Постусловия** | Состояние системы и данных после завершения сценария |
| **Выявленные пробелы** | Неопределённости и противоречия исходных требований |
| **Уточняющие вопросы** | Вопросы, без ответа на которые нельзя однозначно сформировать тест |

## 2. Именование

| Артефакт | Шаблон | Пример |
|---|---|---|
| Journey (suite) | `J<NN>-<slug>` | `J01-onboarding-first-play` |
| Основной кейс | `TC-J<NN>-00` | `TC-J01-00` |
| Кейс-вариант | `TC-J<NN>-<NN>` | `TC-J01-03` |
| Требование | `REQ-<NN>` | `REQ-07` |

Основной кейс — счастливый сквозной путь целиком.
Кейсы-варианты — отклонения от него (ошибки, граничные значения, прерывания), каждый из них
обязан ссылаться на основной кейс полем **Вариант от** и переиспользовать его предусловия.

## 3. Обязательная структура Markdown

```md
# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-00
- **Название:** …
- **Цель:** …
- **Приоритет:** Критический | Высокий | Средний | Низкий
- **Journey:** J01-onboarding-first-play
- **Вариант от:** — | TC-J01-00
- **Покрываемые требования:** REQ-01, REQ-02, REQ-05

## Предусловия

- …

## Тестовые данные

| Параметр | Значение | Комментарий |
|---|---|---|
|  |  |  |

## Шаги

| № | Действие пользователя | Тестовые данные | Ожидаемый результат |
|---:|---|---|---|
| 1 |  |  |  |
| 2 |  |  |  |

## Постусловия

- …

## Выявленные пробелы

- …

## Уточняющие вопросы

1. …
2. …
```

Заголовки разделов приведены дословно и не изменяются.
Поля **Journey**, **Вариант от**, **Покрываемые требования** — расширение эталона, нужное для
связности сюитов и трассируемости; остальные поля соответствуют исходному шаблону.

## 4. Правила заполнения шагов

- Один шаг — одно действие пользователя и один проверяемый результат.
- Столбец «Тестовые данные» содержит конкретное значение либо `—`, если данные не используются.
- Ожидаемый результат описывает наблюдаемое: экран, элемент, текст, состояние, счётчик, порядок.
- Запрещены формулировки: «успешно», «корректно», «работает», «без ошибок», «как ожидается»,
  «выполнено», «нормально», если они не дополнены наблюдаемым признаком.
- Значения, созданные на ранних шагах, повторяются в поздних шагах дословно.
- Минимальная длина сквозного основного кейса — 8 шагов; кейс из 3 шагов не является e2e.
- Максимальная — **2 шага на этап плана**: 8 этапов дают потолок 16. Выше — признак того, что
  одно наблюдаемое раздроблено на несколько шагов. Потолок считается от плана, поэтому длинный
  кейс законен ровно настолько, насколько длинен journey (MAJOR, не BLOCKER: длина сама по себе
  не делает кейс неверным).

## 5. Дополнительный JSON-формат

Markdown не пишется вручную. `qa-designer` пишет только JSON; Markdown порождает
`scripts/json_to_md.py` детерминированно из написанного `.json` — это часть самопроверки
дизайнера, а не отдельный творческий шаг. Причина: ручное дублирование стоило столько же
выходных токенов, сколько сам кейс, и по природе своей рискует стать пересказом вместо
копии — а копия обязана быть точной.

Правка `.md` бессмысленна: следующая генерация её затрёт. Всё, что нужно исправить,
исправляется в `.json`, после чего конвертер запускается заново.

**Строковые поля шага можно писать свободно.** Конвертер экранирует `|` и сворачивает
переводы строк при подстановке в ячейку, а линтер знает про экранирование и не считает
`\|` границей колонки. Запрета больше нет — раньше он был, и держался на памяти автора.

Разметку можно писать значением: линтер отличает её от незаполненного слота по закрывающему
элементу — `</provider>` или `/>`. `<хост>` заглушкой остаётся, `<topology>…</topology>`
проходит. Единственное, что по-прежнему неотличимо, — одиночный открывающий тег без закрытия;
корректный XML таким не бывает.

**Пробелы и вопросы: давайте им явные `id`.** Оба массива принимают две формы —
строку (как раньше) и объект:

```json
"gaps": [
  {"id": "G-03", "text": "Момент появления рекламной вставки не задан…"},
  {"id": "G-J02-1", "text": "Тарифный признак в интерфейсе не описан…"}
],
"clarifyingQuestions": [
  {"id": "Q-03", "text": "Каким событием вызывается рекламная вставка…"}
]
```

Пробел или вопрос, унаследованный из плана, берёт **его** id (`G-03`, `Q-05`) — это связь,
переживающая перенумерацию. Найденный дизайнером получает id вида `G-<journey>-<n>`, который
ни с чем не столкнётся.

Шаг ссылается по id: «…требованиями не задано (G-03, Q-03)». Линтер проверяет, что ссылка
разрешается, — правило `ref-dangling`. Позиционные ссылки («пробел 3») он тоже проверяет, но
позиция ломается молча: вставка одного вопроса сдвигает все последующие, а текст шага остаётся
прежним. Шесть из семи MINOR одного из прогонов были ровно этим.

**Ссылки на тестовые данные.** В колонке `steps[].testData` параметр называется ссылкой
`{Имя параметра}` — конвертер подставляет значение из таблицы «Тестовые данные» на место
ссылки, поэтому композиция работает: `{Базовый URL шлюза}/gateway/admin/api/v1/topologies`.
Литеральные фигурные скобки пишутся как `{{` и `}}`.

Ссылка обязывает: имя, которого нет в таблице, — BLOCKER `testdata-ref-unknown`, и в Markdown
такая ссылка остаётся неразрешённой, чтобы дефект был виден в самом артефакте. Строка таблицы,
на которую никто не сослался и чьё значение не встречается в шагах, — MAJOR `data-unused`.
Вклеивать значение текстом по-прежнему можно: проверка использования тогда идёт подстрокой,
как раньше.

Раздел **«Трассируемость»** в Markdown порождается из этого поля: таблица «требование →
шаги», где объявленное кейсом требование без единого шага показано прочерком. Раздел
необязательный — его нет, если якорей нет ни у одного шага, — и вручную не пишется.

Поле `steps[].requirements` **проверяется** линтером: якоря должны существовать в индексе
требований, не выходить за «Покрываемые требования» кейса, и каждое объявленное кейсом
требование обязано проверяться хотя бы одним шагом. Критик сверяет с ним свою карту
трассируемости. Это единственное, что нельзя восстановить из Markdown: таблица
«Шаги» не несёт колонки с якорями требований (только `## Общая информация` → «Покрываемые
требования» на уровне всего кейса). Заполняйте его: из него порождается раздел
«Трассируемость», по нему работают три правила линтера, и с ним сверяется критик.

```json
{
  "id": "",
  "title": "",
  "goal": "",
  "priority": "",
  "journeyId": "",
  "variantOf": null,
  "requirements": [],
  "preconditions": [],
  "testData": [
    { "name": "", "value": "", "comment": "" }
  ],
  "steps": [
    {
      "number": 1,
      "action": "",
      "testData": "",
      "expectedResult": "",
      "requirements": []
    }
  ],
  "postconditions": [],
  "gaps": [],
  "clarifyingQuestions": []
}
```

JSON обязан быть содержательно идентичен Markdown-версии кейса — это гарантируется механически,
конвертером, а не проверяется постфактум на глаз.
