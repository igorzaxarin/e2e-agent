## 📋 О проекте

**E2E Test Case Factory** — это плагин для GigaCode (CLI-инструмент SBER), который автоматизирует создание сквозных (end-to-end) тест-кейсов на основе текстовых требований к продукту.

Система работает в **три этапа**:

```
Требования (Markdown)
       ↓
┌──────────────────────────────────────┐
│  🤖 requirements-analanalyst           │  →  output/suites/ + _index.json
│  (1 раз, над всеми требованиями)      │
└──────────────────────────────────────┘
       ↓
┌──────────── ШЛЮЗ ТРЕБОВАНИЙ ─────────────┐
│  Вам показывают все пробелы, противоречия, │
│  неохваченные требования и блокирующие     │
│  вопросы. Вы решаете, что делать.          │
└────────────────────────────────────────────┘
       ↓
  ┌─────────── parallel P ────────────┐
  │   designer J01    designer J02    │  →  output/cases/<J>/  (Markdown + JSON)
  │   designer J03    ...             │
  └────────────────────────────────────┘
       ↓
  ┌─────────── parallel P ────────────┐
  │   test-critic J01  critic J02     │  →  output/reviews/ + state/
  │   test-critic J03   ...            │
  └────────────────────────────────────┘
       ↓
  ┌───────────── ШЛЮЗ ПОКРЫТИЯ ───────────────┐
  │  Показывается, что не удалось урегулировать │
  └─────────────────────────────────────────────┘
       ↓
  ┌───────────── ОПЦИОНАЛЬНО ────────────────┐
  │  pytest-stub-writer → output/tests/<J>/    │
  └─────────────────────────────────────────────┘
       ↓
  output/report.md
```

**Ключевая идея:** пробелы в требованиях **не поглощаются моделью**, а показываются человеку.  
Человек решает: ответить на вопросы сейчас, зафиксировать как пробелы, или остановить прогон.

```bash
/e2e:run
```

Система:
1. Запускает аналитика над `input/requirements/*.md`
2. Показывает вам **все пробелы** и спрашивает, как поступить
3. Запускает `P` параллельных циклов designer→critic
4. Показывает финальный отчёт

**Результат:** `output/report.md` с итогами по всем journey.

## 🧠 Архитектура и принципы

### 🔄 Три агента в цикле

**1. Requirements Analyst (аналитик требований)**

- Читает **все** `input/requirements/*.md`
- Группирует требования по **end-to-end journey** (не по фичам, не по экранам)
- Пишет планы в `output/suites/` и машинный индекс `_index.json`
- **Правило:** journey пересекает ≥3 функциональных области и имеет ≥5 этапов
- **Правило:** данные, созданные на раннем этапе, потребляются на позднем

**2. QA Designer (дизайнер тестов)**

- Владеет **ровно одним** journey
- Пишет тест-кейсы в `output/cases/<JOURNEY_ID>/`
- **Формат:** обязательный русский язык
- **Минимальный основной кейс:** ≥8 шагов; **максимальный:** ≤2 шага на этап плана
- **Каждый шаг** = 1 действие + 1 наблюдаемый результат

**3. Test Critic (критик)**

- Ревьюит кейсы одного journey
- **Обязательно:** сначала запускает `scripts/validate_cases.py`
- Вердикты: `PASS` / `FIX_REQUIRED` / `NEEDS_HUMAN`
- **BLOCKER:** выдуманное поведение или неопределённый результат
- **MAJOR:** всё остальное

### ⚖️ Шкала severity (из `docs/critic-rubric.md`)

| Степень | Что означает | Что делать |
|---|---|---|
| **BLOCKER** | Выдуманное поведение / неопределённый результат | Обязательно исправить, иначе кейс не проходит |
| **MAJOR** | Нарушение критерия качества | Исправить, если возможно без выдумывания |
| **MINOR** | Косметическое / стилистическое | Можно отложить |

### 🔑 12 критериев качества (из `docs/quality-criteria.md`)

1. **Полнота** — каждое требование покрыто
2. **Связность** — данные переходят между шагами
3. **Атомарность** — один шаг = одно действие
4. **Проверяемость** — каждый результат наблюдается
5. **Изолированность** — кейс не зависит от других
6. **Независимость** — ничего не выдумано
7. **Воспроизводимость** — одни и те же данные = один и тот же результат
8. **Читаемость** — русский, понятные имена
9. **Структурированность** — заголовки по `docs/format.md`
10. **Параллельность** — можно запускать с другими
11. **Покрытие** — все REQ-XX охвачены
12. **Устойчивость** — стабы возвращают детерминированные ответы

## 💻 Команды

### `/e2e:run` — полный цикл

**Формат:**

```
/e2e:run [--пыть <путь>] [--max N] [--parallel N] [--unit journey|area] [--journey J01] [--yes] [--no-ask] [--generate-pytest]
```

**Параметры:**

| Параметр | Значение | По умолчанию |
|---|---|---|
| `путь` | `input/requirements/*.md` или другой glob | `input/requirements/*.md` |
| `--max N` | Максимум итераций на journey | `3` |
| `--parallel N` | Сколько циклов параллельно | Спрашивает |
| `--unit journey` | Один journey на цикл | `journey` |
| `--unit area` | Одна функциональная область | — |
| `--journey J01` | Только один journey | Все |
| `--yes` | Пропустить паузу go/no-go | Нет |
| `--no-ask` | Полностью автономно | Нет |
| `--generate-pytest` | Генерировать тесты pytest после | Нет |

**Процесс:**

```
Фаза 1 — Анализ
  → agent(requirements-analyst)
  → читает output/suites/_index.json
  → показывает вам: непокрытые REQ, пробелы, блокирующие вопросы

Фаза 1.5 — Шлюз
  → вы решаете: продолжить / ответить / остановить

Фаза 2 — Дизайн + ревью (P раз)
  → P × agent(qa-designer) + P × agent(test-critic)
  → каждый цикл: designer → critic → fix → designer → critic → ...
  → max 3 итерации

Фаза 2.5 — Pytest (опционально)
  → Спрашивает: «Сгенерировать pytest-тесты?»
  → agent(pytest-stub-writer) для каждого PASS journey
  → agent(browser-test-writer) — только при --selenium и заданном --base-url

Фаза 3 — Шлюз покрытия
  → показывает непокрытые требования, открытые вопросы

Фаза 4 — Отчёт
  → output/report.md
```

**Пример:**

```bash
/e2e:run --max 2 --parallel 3 --unit journey
```

### `/e2e:analyze` — только анализ

Запускает только `requirements-analyst`. Показывает планы journey.

```
/e2e:analyze [путь]
```

### `/e2e:design` — только дизайн

Запускает только `qa-designer` для указанных journey.

```
/e2e:design J01 [J02 ...]
```

### `/e2e:review` — только ревью

Запускает только `test-critic` для указанных journey.

```
/e2e:review J01 [J02 ...] [N]
```

### `/e2e:status` — текущее состояние

Показывает:
- Все suite-планы
- Все тест-кейсы
- Все ревью
- Текущие вердикты
- Количество блокеров
- Открытые вопросы

## 🧪 Линтер (детерминированный)

Перед каждым ревью **обязательно** запускается:

```bash
python3 scripts/validate_cases.py output/cases/<JOURNEY_ID>
```

**Что проверяет:**

| № | Проверка | Severity |
|---|---|---|
| 1 | Все обязательные секции присутствуют | BLOCKER |
| 2 | Нет `<placeholder>` | BLOCKER |
| 3 | Нет «успешно», «корректно», «работает» | BLOCKER |
| 4 | Ступенчатая нумерация (1, 2, 3…) | BLOCKER |
| 5 | Основной кейс ≥ 8 шагов | BLOCKER |
| 5а | Основной кейс ≤ 2 шага на этап плана | MAJOR |
| 6 | Каждый шаг = 1 действие | MAJOR |
| 7 | Данные из таблицы используются в шагах | MAJOR |
| 8 | Markdown и JSON совпадают | MAJOR |
| 9 | Варианты ссылаются на основной кейс | MAJOR |
| 10 | Нет выдуманного поведения | BLOCKER |

**Exit code:** `1` = есть BLOCKER, `0` = всё прошло.

## 📝 Формат тест-кейса (из `docs/format.md`)

Обязательные поля (все на русском):

```
# TC-J<NN>-<MM>: <Название варианта>

## Связанные REQ
- REQ-XX

## Предусловия
- Учётная запись создана
- Пользователь авторизован
- ...

## Тестовые данные
| Параметр | Значение |
|---|---|
| phone | +7 999 000-00-11 |

## Шаги
| № | Действие | Ожидаемый результат | REQ |
|---|---|---|---|
| 1 | ... | ... | REQ-XX |

## Постусловия
...

## Выявленные пробелы
...

## Уточняющие вопросы
...
```

**Правила:**

- **Один шаг = одно действие.** Нельзя «нажать кнопку и проверить, что…» — это два шага
- **Ожидаемый результат — наблюдаемый.** Экран, элемент, текст, состояние, счётчик, порядок
- **Запрещено:** «успешно», «корректно», «работает», «без ошибок», «как ожидается»
- **Данные из тестовой таблицы** — никаких литералов в шагах
- **Связность:** значение, созданное на шаге 5, повторяется на шаге 12

## ⚙️ Адаптация к другому продукту

1. **Замените** `input/requirements/*.md` на свои требования
2. **Если нужно** — отредактируйте `docs/format.md`, `templates/test-case.md` под свой формат
3. **Ничего в `.gigacode/agents/` менять не нужно** — агенты читают формат из `docs/`

## 🛡️ Безопасность и ограничения

- **Никаких выдуманных реакций.** Если система не определяет поведение — это пробел, а не ожидаемый результат
- **Никаких секретов в тестах.** `test_data.py` содержит только константы, не токены
- **Никакой агрегации в кейсах.** Один кейс = один journey = один файл

## 📝 Примечания

1. **Русский — обязательный язык артефактов.** Английский только в комментариях кода и коммитах
2. **Никаких placeholder.** Если тест не может определить ожидаемый результат — это BLOCKER
3. **Данные — единственный источник правды.** Ответы в `_answers.md` = требования
4. **Параллельность — максимальная.** Все designer в одном сообщении, все critic в одном
5. **Изоляция.** Один critic никогда не пишет `output/state.json`
