# Требования к шлюзу Apache Knox — демонстрационный сценарий

> Минимальный корпус для быстрого демо-прогона фабрики: один сквозной сценарий
> «развернуть топологию — записать и прочитать файл через шлюз — удалить топологию».
> Наблюдаемые заданы явно: HTTP-коды, заголовки, поля JSON.

## Аутентификация

- **REQ-01.** Любой запрос через шлюз требует Basic-аутентификации против LDAP.
  В демонстрационном LDAP две учётные записи: `admin` / `admin-password` и
  `guest` / `guest-password`. Запрос с неверным паролем возвращает HTTP 401,
  тело ответа содержит текст `Authentication failed`. Запрос с верными учётными
  данными передаётся сервису; код ответа определяется операцией (REQ-02…REQ-06).

## Администрирование топологий

- **REQ-02.** Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>`
  от `admin` с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS)
  возвращает HTTP 200. Не позднее чем через 30 секунд топология присутствует в ответе
  `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`),
  а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05.
  Перед деплоем топологии с этим именем в списке `GET …/topologies` нет.

## Проксирование WebHDFS

- **REQ-03.** Запрос `GET https://<хост>:8443/gateway/<имя>/webhdfs/v1/tmp?op=LISTSTATUS`
  от аутентифицированного пользователя возвращает HTTP 200 и JSON с полем `FileStatuses`.
- **REQ-04.** Запрос `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true`
  с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла.
- **REQ-05.** Запрос `GET …/webhdfs/v1/<путь к файлу>?op=OPEN` возвращает HTTP 200
  и содержимое, байт в байт совпадающее с загруженным в REQ-04.

## Жизненный цикл топологии

- **REQ-06.** Запрос `DELETE …/admin/api/v1/topologies/<имя>` от `admin` возвращает
  HTTP 200. После удаления топология отсутствует в списке `GET …/topologies`,
  а запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404.
