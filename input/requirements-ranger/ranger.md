# Бизнес-требования к централизованному управлению доступом на Apache Ranger 2.5

## 1. Бизнес-контекст и проблема

Apache Ranger — фреймворк централизованного управления, контроля и аудита доступа к данным в экосистеме Hadoop. Он решает задачу единообразной авторизации в мультиарендной среде озера данных, где доступ к одним и тем же данным запрашивают разные подразделения, сервисы и процессы.

Ranger состоит из трёх взаимодействующих частей:
- **Ranger Admin** — веб-консоль и REST API, единая точка описания политик;
- **плагины** — встраиваются в защищаемые сервисы (HDFS, Hive, HBase, Kafka, Ozone, Trino, Knox, YARN, Solr), периодически скачивают политики из Ranger Admin и принимают решение о доступе локально;
- **подсистема аудита** — собирает записи о каждом решении плагина и о каждом действии администратора.

Пользовательский путь администратора безопасности включает:
- вход в консоль Ranger Admin;
- регистрацию защищаемого сервиса;
- создание ресурсных политик доступа;
- настройку маскирования данных и построчной фильтрации;
- работу с тег-политиками;
- выделение зон безопасности и делегирование прав на них;
- управление пользователями, группами и ролями;
- проверку того, что политика доехала до плагина и вступила в силу;
- разбор записей аудита;
- выход и повторный вход в консоль.

Поведение системы существенно различается для трёх типов учётных записей: **администратора Ranger** (роль `ROLE_SYS_ADMIN`), **делегированного администратора зоны** (zone admin) и **аудитора** (`ROLE_ADMIN_AUDITOR` — администратор с доступом только на чтение; роль `ROLE_KEY_ADMIN_AUDITOR` относится к Ranger KMS и вне рамок). Требования должны обеспечить предсказуемое поведение на всём пути и корректное сохранение конфигурации между сессиями.

Текущие требования описывают существующее поведение Apache Ranger 2.5.0 (выпуск от 7 августа 2024 года) и отдельные целевые изменения.

**Целевым изменением** является внедрение временного (срочного) доступа: в версии 2.5 у элемента политики появился **срок действия** (validity period, RANGER-3815), позволяющий выдавать права на ограниченный период без ручного отзыва.

Вторым фактором, влияющим на проверки, является полная миграция веб-консоли с Backbone.js на React 18.2.0 и переход на левое боковое меню, выполненные в этой же версии.

### 3.2. Базовые функциональные требования

| ID | Бизнес-требование | Детализация | Приоритет |
| :--- | :--- | :--- | :--- |
| **BR-001** | **Авторизация в консоли Ranger Admin** | **Тип входа:** пользователь входит по имени учётной записи и паролю в веб-консоли Ranger Admin.<br>**Учётные записи:** используются заранее созданные и активные учётные записи.<br>**Роли:** должны быть подготовлены учётная запись администратора Ranger, учётная запись администратора зоны и учётная запись аудитора.<br>**Ошибочный пароль:** при вводе неверного пароля консоль показывает ошибку, не выполняет вход и позволяет повторить ввод.<br>**Корректный пароль:** после успешного входа открывается стартовая страница консоли.<br>**Внешние источники:** учётные записи могут приходить из LDAP/AD через usersync; конкретный источник для тестового стенда не фиксируется.<br>**Простой сессии:** сессия завершается по неактивности; конкретное значение таймаута не задано и берётся из конфигурации стенда. | **Must** |
| **BR-002** | **Управление защищаемыми сервисами** | **Раздел:** сервисы отображаются в Service Manager, сгруппированные по типу сервиса.<br>**Создание:** администратор может зарегистрировать сервис выбранного типа, указав имя и параметры подключения.<br>**Редактирование:** параметры зарегистрированного сервиса могут быть изменены.<br>**Удаление:** сервис может быть удалён.<br>**Типы сервисов:** в 2.5 поддерживаются в том числе HDFS, Hive, HBase, Kafka, Knox, YARN, Solr, Ozone и Trino.<br>**Проверка подключения:** консоль предоставляет проверку подключения к сервису.<br>**Поведение при недоступном сервисе:** результат проверки подключения к недоступному сервису не определён в требованиях. | **Must** |
| **BR-003** | **Ресурсные политики доступа** | **Объект политики:** политика описывает набор ресурсов сервиса — для Hive это база, таблица и колонка, для HDFS путь, для Kafka топик.<br>**Шаблоны:** ресурсы могут задаваться с использованием подстановочных символов.<br>**Субъекты:** права выдаются пользователям, группам и ролям.<br>**Права:** набор прав определяется типом сервиса (для Hive — select, update, create, drop, alter и другие).<br>**Разрешение:** элемент политики разрешает перечисленные права указанным субъектам.<br>**Версионирование:** при сохранении политика получает новую версию.<br>**Включение и отключение:** политика может быть отключена без удаления.<br>**Уникальность имени:** поведение при сохранении политики с именем, уже существующим в этом сервисе, не определено в требованиях. | **Must** |
| **BR-004** | **Запреты и исключения** | **Запрет:** политика может явно запрещать права пользователям, группам и ролям.<br>**Исключения из разрешения:** из выданного разрешения может быть исключено подмножество субъектов.<br>**Исключения из запрета:** из запрета может быть исключено подмножество субъектов.<br>**Приоритет:** правила приоритета между разрешением и запретом в рамках одной политики требованиями не описаны и должны проверяться фактически.<br>**Доступность:** блоки запретов и исключений доступны не для всех типов сервисов; конкретный перечень не фиксируется. | **Must** |
| **BR-005** | **Маскирование данных** | **Тип политики:** отдельный тип политики — маскирование (masking).<br>**Область:** маскирование задаётся на уровне колонки.<br>**Способы:** поддерживаются предопределённые способы маскирования — в том числе полное маскирование, маскирование всех цифр, показ первых или последних символов, хеш, значение NULL.<br>**Пользовательское выражение:** способ маскирования может задаваться пользовательским выражением.<br>**Результат:** субъект, попавший под политику, получает преобразованное значение вместо исходного.<br>**Поддержка:** маскирование поддерживается не всеми типами сервисов; в требованиях фиксируется только Hive. | **Must** |
| **BR-006** | **Построчная фильтрация** | **Тип политики:** отдельный тип политики — построчный фильтр (row-level filter).<br>**Область:** фильтр задаётся на уровне таблицы.<br>**Выражение:** условие фильтра задаётся выражением, вычисляемым при обращении.<br>**Результат:** субъект, попавший под политику, видит только подмножество строк.<br>**Сочетание:** построчная фильтрация и маскирование могут действовать одновременно; порядок их применения в требованиях не описан.<br>**Поддержка:** в требованиях фиксируется только Hive. | **Must** |
| **BR-007** | **Тег-политики** | **Источник тегов:** классификации ресурсов приходят из внешнего сервиса управления метаданными (например, Apache Atlas) либо из файлового источника тегов.<br>**Назначение:** политика описывает доступ к классификации, а не к конкретному ресурсу.<br>**Приоритет:** тег-политики в общем случае вычисляются раньше ресурсных политик.<br>**Атрибуты:** в условиях могут использоваться атрибуты тега.<br>**Обновление:** в 2.5 файловый источник тегов поддерживает передачу изменений (tag deltas), а не только полного набора.<br>**Разрешение конфликтов:** поведение при конфликте тег-политики и ресурсной политики в требованиях не описано. | **Should** |
| **BR-008** | **Зоны безопасности** | **Назначение:** зона объединяет ресурсы и политики в отдельную группу для делегирования администрирования.<br>**Создание:** администратор указывает имя зоны, описание, администраторов зоны, аудиторов зоны, ресурсные и тег-сервисы.<br>**Принадлежность ресурса:** один ресурс относится не более чем к одной зоне.<br>**Вычисление доступа:** если ресурс попадает в зону, доступ определяется только политиками этой зоны; если не попадает ни в одну — политиками зоны по умолчанию (безымянной).<br>**Права администратора Ranger:** администратор Ranger управляет любыми зонами и политиками в них независимо от того, назначен ли он администратором зоны.<br>**Конфликт ресурсов:** поведение при попытке отнести ресурс, уже принадлежащий другой зоне, требованиями не описано. | **Must** |
| **BR-009** | **Делегированное администрирование** | **Администратор зоны:** может создавать, изменять и удалять политики сервисов, связанных с его зоной.<br>**Аудитор зоны:** может просматривать политики и записи аудита своей зоны, но не изменять их.<br>**Граница полномочий:** действия администратора зоны за пределами его зоны недоступны.<br>**Делегирование на уровне политики:** отдельной политикой набор пользователей, групп и ролей может получить право администрировать подмножество ресурсов и прав.<br>**Отображение в консоли:** различия интерфейса между ролями в требованиях не описаны и должны проверяться фактически. | **Must** |
| **BR-010** | **Пользователи, группы и роли** | **Раздел:** управление ведётся в разделе настроек консоли.<br>**Источники:** учётные записи и группы создаются вручную либо синхронизируются из внешнего каталога через usersync.<br>**Атрибуты:** usersync может переносить атрибуты пользователей и групп (например, подразделение или расположение), которые затем используются в условиях политик.<br>**Роль:** роль — это объединение пользователей, групп и других ролей.<br>**Управление ролями:** роли создаются и изменяются через консоль и REST API.<br>**Перенос ролей:** в 2.5 доступны REST API импорта и экспорта ролей.<br>**Принудительное удаление:** в 2.5 доступны REST API принудительного удаления пользователей и групп.<br>**Последствия удаления:** поведение политик, ссылающихся на удалённого пользователя или группу, в требованиях не описано. | **Must** |
| **BR-011** | **Срок действия элемента политики** | **Целевое изменение:** элемент политики может иметь срок действия — дату и время начала и окончания.<br>**Внутри срока:** права, выданные элементом политики, действуют.<br>**После окончания:** права прекращают действовать без ручного отзыва и без удаления политики.<br>**До начала:** права не действуют.<br>**Часовой пояс:** трактовка часового пояса границ срока в требованиях не зафиксирована.<br>**Момент прекращения:** задержка между наступлением границы срока и фактическим прекращением доступа на плагине не определена и зависит от периода обновления политик.<br>**Отображение:** способ отображения истёкшего элемента политики в консоли в требованиях не описан. | **Must** |
| **BR-012** | **Распространение политик на плагины** | **Механизм:** плагин периодически обращается к Ranger Admin и скачивает изменившиеся политики.<br>**Локальное решение:** решение о доступе принимается плагином локально по последнему скачанному набору политик.<br>**Версия:** у скачанного набора есть номер версии, сопоставимый с версией в консоли.<br>**Статус плагинов:** консоль отображает состояние подключённых плагинов и время последнего обновления.<br>**Период обновления:** конкретное значение периода не задаётся требованиями и берётся из конфигурации стенда.<br>**Недоступность Ranger Admin:** плагин продолжает работать по последнему скачанному набору политик; предельная длительность такой работы требованиями не ограничена. | **Must** |
| **BR-013** | **Аудит** | **Журнал доступа:** фиксируются обращения к защищённым ресурсам с результатом решения, субъектом, ресурсом, правом и сработавшей политикой.<br>**Журнал администрирования:** фиксируются изменения политик, сервисов, зон, пользователей, групп и ролей.<br>**Сессии:** фиксируются входы в консоль.<br>**Состояние плагинов:** фиксируется факт и время скачивания политик плагинами.<br>**Синхронизация:** фиксируются результаты работы usersync.<br>**Фильтры аудита:** объём записей может ограничиваться фильтрами аудита на уровне сервиса.<br>**Задержка появления записи:** время от события до появления записи в консоли требованиями не задано.<br>**Срок хранения:** глубина хранения записей требованиями не задана. | **Must** |
| **BR-014** | **Различия полномочий по ролям** | **Администратор Ranger:** полный доступ ко всем описанным функциям, включая зоны, сервисы, политики, пользователей и аудит.<br>**Администратор зоны:**<br>- управляет политиками сервисов своей зоны<br>- не управляет политиками за пределами своей зоны<br>- не управляет составом зоны, если это не предусмотрено отдельно<br>**Аудитор:**<br>- получает представление администратора в режиме только для чтения<br>- заблокирован для операций создания, изменения, удаления, импорта и экспорта — как в консоли, так и через REST API<br>**Проверка:** различия должны проверяться отдельными сценариями под каждой учётной записью. | **Must** |

### 3.3. Негативные сценарии

| ID | Сценарий | Ожидаемое поведение | Приоритет |
| :--- | :--- | :--- | :--- |
| **BR-015** | Ввод неверного пароля при входе в консоль | Консоль показывает ошибку, не выполняет вход, позволяет повторить ввод | **Must** |
| **BR-016** | Администратор зоны открывает политику вне своей зоны | Изменение недоступно; конкретная реакция интерфейса требованиями не описана — требуется фактическая проверка | **Must** |
| **BR-017** | Аудитор пытается изменить политику через консоль и через REST API | Операция не выполняется в обоих случаях; способ, которым консоль это показывает (скрытие, блокировка или сообщение), требованиями не описан — требуется фактическая проверка | **Must** |
| **BR-018** | Отнесение ресурса, уже принадлежащего другой зоне, ко второй зоне | Поведение не определено в требованиях — требуется фактическая проверка | **Should** |
| **BR-019** | Сохранение политики с именем, уже существующим в этом сервисе | Поведение не определено в требованиях — требуется фактическая проверка | **Should** |
| **BR-020** | Обращение к ресурсу после истечения срока действия элемента политики | Доступ прекращается; момент прекращения зависит от периода обновления политик на плагине | **Must** |
| **BR-021** | Обращение к ресурсу при недоступном Ranger Admin | Плагин принимает решение по последнему скачанному набору политик | **Should** |
| **BR-022** | Сохранение политики без указания ресурса или без единого субъекта | Поведение не определено в требованиях — требуется фактическая проверка | **Could** |

## 6. Допущения и риски

| ID | Тип | Описание | Митигация |
| :--- | :--- | :--- | :--- |
| **AS-01** | Допущение | Проверки выполняются на Apache Ranger версии 2.5.0 | Зафиксировать версию стенда до начала проверок |
| **AS-02** | Допущение | Ranger Admin и хотя бы один защищаемый сервис с установленным плагином развёрнуты и доступны | Подготовить стенд до начала проверок |
| **AS-03** | Допущение | Подготовлены три учётные записи: администратор Ranger, администратор зоны, аудитор | Создать учётные записи заранее |
| **AS-04** | Допущение | Подготовлен фиксированный тестовый набор данных в Hive с чувствительной колонкой | Создать базу, таблицу и колонки заранее |
| **AS-05** | Допущение | Администратор работает в поддерживаемом браузере | Проверять сценарии в Chrome, Firefox, Safari и Edge |
| **AS-06** | Допущение | Часы Ranger Admin и защищаемых сервисов синхронизированы | Проверить синхронизацию времени до проверок срока действия |
| **RS-01** | Риск | Вступление политики в силу не мгновенно: плагин обновляет политики периодически | Не проверять эффект сразу после сохранения; ориентироваться на версию политики у плагина |
| **RS-02** | Риск | Период обновления политик не задан требованиями и различается на стендах | Считать значение параметром стенда, а не константой сценария |
| **RS-03** | Риск | Полная миграция консоли на React 18 в версии 2.5 изменила разметку интерфейса | Не переносить локаторы из сценариев для версий до 2.5 |
| **RS-04** | Риск | Набор прав и возможность маскирования различаются по типам сервисов | Проверять маскирование и фильтрацию только на зафиксированном в требованиях Hive |
| **RS-05** | Риск | Приоритет тег-политик над ресурсными описан в общем виде и может зависеть от конфигурации | Проверять конфликт тег-политики и ресурсной политики отдельным сценарием |
| **RS-06** | Риск | Учётные записи из внешнего каталога могут появляться и исчезать по расписанию usersync | Использовать учётные записи, созданные вручную |
| **RS-07** | Риск | Проверка срока действия требует ожидания реального времени | Задавать короткие интервалы; фиксировать ожидаемое время прекращения доступа явно |
| **RS-08** | Риск | Задержка появления записи аудита не определена | Проверять наличие записи с явно заданным ожиданием, а не мгновенно |
| **RS-09** | Риск | Неопределённости могут привести к разным трактовкам поведения | Явно фиксировать неоднозначности и не делать предположений |

## 7. Открытые вопросы и неоднозначности

3. Что происходит при попытке отнести ресурс, уже принадлежащий одной зоне, ко второй зоне.
4. Допускается ли сохранение двух политик с одинаковым именем в одном сервисе.
5. В каком часовом поясе трактуются границы срока действия элемента политики.
6. Через какое время после истечения срока действия доступ гарантированно прекращается на плагине.
7. Как консоль отображает элемент политики с истёкшим сроком действия.
8. Что происходит с политиками, ссылающимися на пользователя или группу, удалённых принудительно через REST API.
9. Какова предельная длительность работы плагина по последнему скачанному набору политик при недоступном Ranger Admin.
10. Какие элементы интерфейса скрываются, а какие блокируются для аудитора и администратора зоны.
11. Каково значение таймаута неактивности сессии консоли и как он проявляется для пользователя.
12. В каком порядке применяются маскирование и построчная фильтрация, если обе политики действуют на одну таблицу.
13. Какое поведение ожидается при сохранении политики без ресурса или без единого субъекта.
14. Какова глубина хранения записей аудита и что происходит с записями по её истечении.
